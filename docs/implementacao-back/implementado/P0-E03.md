O ledger schema_migrations é criado dentro da transação após adquirir o advisory lock, evitando corrida no primeiro bootstrap. A inicialização Docker cria blog_app separado do migrador, sem privilégios DDL. Migrations novas são incrementais; as já aplicadas não foram reescritas.

Evidências consolidadas e limites: [AUDITORIA-P0](./AUDITORIA-P0.md). Esta revisão prevalece sobre o relato histórico abaixo, inclusive trechos que anunciam como futuras etapas já executadas.

## Escopo interpretado

Esta entrega segue a fase **P0-E03** de `BACKEND_IMPLEMENTATION_PLAN.md` e os requisitos R04/R08/R17/R19/R22/R23 referenciados por ela. O objetivo desta fase é estabelecer a base segura de PostgreSQL antes das migrations de conteúdo das próximas fases: a aplicação faz somente DML; um processo de migrador, com credenciais próprias, faz DDL; e o histórico de schema é verificável.

Nesta etapa não foram criadas tabelas de domínio editorial. Elas pertencem a P0-E05, não a P1/P2, e entram como novas migrations imutáveis.

## Alterações realizadas

- A conexão foi centralizada em `src/infrastructures/database.ts`. Ela configura pool, limites de aquisição e consulta, faz `authenticate()` no startup, oferece verificação de prontidão e fecha de forma idempotente. Não existe `sync()`, `alter` automático ou outro DDL no processo da API.
- Foi removida a infraestrutura ORM antiga baseada em `sequelize-typescript`; o projeto usa Sequelize com o driver `pg` diretamente.
- Foi criado `migrations/runner.ts`. Ele ordena versões, valida metadados, calcula checksum SHA-256, mantém `schema_migrations(version, checksum, applied_at)`, detecta duplicidade e alteração de arquivo já aplicado.
- O runner cria o ledger apenas no caminho de migração. `migrationStatus` é somente leitura e trata a ausência inicial da tabela como histórico vazio.
- Cada execução de migration usa transação PostgreSQL com `pg_advisory_xact_lock` e prazo de lock. O DDL de cada item e o registro correspondente no ledger ficam na mesma transação; erro reverte ambos. Execuções concorrentes são serializadas e a segunda não reaplica versões já registradas.
- Foi criado `scripts/migrate.ts` e os comandos `npm run migrate` e `npm run migrate:status`. O comando exige `MIGRATOR_DB_*`; as credenciais de `DB_*` continuam reservadas à aplicação. A primeira migration, `001-bootstrap`, estabelece somente o histórico inicial.
- `.env.example` documenta variáveis do migrador sem incluir segredos reais.
- `docker-compose-test.yml` agora usa PostgreSQL 16 e cria `blog_app` com privilégios mínimos. O usuário `blog_migrator` é o dono do banco de teste; o usuário da aplicação só recebe `CONNECT`/`USAGE` e grants explícitos nas tabelas criadas.
- A workflow de CI foi ajustada para reproduzir esses dois papéis e entregar as variáveis de teste ao gate integrado.

## Como foi definido o que mudar

1. A fase P0-E03 define a separação entre processo de API e processo de schema, a tabela de ledger, checksum, lock e testes contra PostgreSQL real.
2. As referências R04 e R08 determinam que o schema não pode ser sincronizado pela aplicação e que migrations devem ser ordenadas, transacionais e auditáveis.
3. R17 e R19 orientam pool, timeouts, readiness e encerramento seguro já presentes na infraestrutura de E02; a nova classe preserva esses contratos.
4. R22 e R23 exigem testes com banco isolado, nome protegido por `blog_test_*` e credenciais diferentes. Por isso os helpers recusam alvo inseguro antes de abrir conexão e o compose/CI criam dois usuários.

## Validação executada

- `npm run ci`: 35 testes aprovados, incluindo lint, typecheck, testes unitários, API, integração e build.
- Integração real em PostgreSQL 16: reaplicação sem duplicidade, migradores concorrentes, rollback de DDL e ledger, checksum divergente, DML permitido à aplicação, DDL recusado ao papel da aplicação e saturação limitada do pool.
- Artefato compilado: `npm run migrate` aplicou `001-bootstrap`; `npm run migrate:status` mostrou a versão e checksum registrados.

## Como continuar a implementação

Para cada próxima fase, comece no item correspondente de `BACKEND_IMPLEMENTATION_PLAN.md`, leia seus requisitos Rxx e os documentos referenciados antes de alterar código. Quando uma fase precisar de schema, crie uma nova migration numerada em `migrations/` com versão única e DDL reversível por transação PostgreSQL. Não edite uma migration já aplicada: o checksum deve falhar de propósito.

Execute migrations em ambiente real apenas pelo job/credencial de migrador. A API deve receber a credencial de aplicação, sem `CREATE`, `ALTER`, `DROP` ou permissões de proprietário. Para testes, suba o compose com `npm run test:database:up`, use somente bancos `blog_test_*`, e encerre com `npm run test:database:down`.

As fases seguintes devem adicionar tabelas, índices, constraints e grants mínimos junto com seus casos de uso, preservando o contrato de P0-E03: DDL versionado no migrador, DML na aplicação e cobertura real de concorrência, rollback e privilégios.
