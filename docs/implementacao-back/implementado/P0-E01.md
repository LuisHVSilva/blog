## 3. Decisões que merecem explicação

### JavaScript de produção sem aliases

O TypeScript entende os antigos aliases para encontrar os arquivos durante a compilação, mas não os converte automaticamente em caminhos relativos no JavaScript. Por isso o build podia passar e a execução falhar.

Os consumidores foram corrigidos, `paths` foi removido e `dev` deixou de carregar `tsconfig-paths/register`. `npm start` executa **`node dist/src/index.js`**. A entrada só será movida para `main.ts` na E02, com atualização dos scripts e testes consumidores.

### Runner e suítes vazias

O runner procura recursivamente arquivos `*.test.ts`, `*.test.js`, `*.test.mjs` e `*.test.cjs` em `tests/unit`, `tests/integration` e `tests/api`, com ordenação estável e argumentos explícitos para o processo Node. Isso funciona também quando o shell Windows não expande globs ou o caminho contém espaços.

`npm test` exige as suítes unitária e de integração. Quando `tests/api` existir, ela também será incluída e precisará conter testes. Solicitar explicitamente uma suíte ausente ou vazia falha. Portanto, **`npm run test:api` retorna erro nesta etapa**, pois a E01 não cria API nem suíte HTTP. Esse comportamento é intencional: não há comando que finja ter validado testes inexistentes.

O runner propaga o código de saída do processo de testes e rejeita argumentos desconhecidos. `--root <diretório>` permite testar a descoberta em fixtures isoladas. A variável interna `NODE_TEST_CONTEXT` é retirada dos subprocessos para que os testes do próprio runner executem um harness independente.

### Lint com o compilador já existente

Foi mantido **TypeScript 7.0.2**. O metadata consultado para `typescript-eslint@8.70.0` declarava suporte a TypeScript `>=4.8.4 <6.1.0`; instalar essa combinação exigiria contrariar o contrato de compatibilidade ou rebaixar o compilador sem necessidade.

Foram escolhidos `eslint@10.10.0`, `@babel/eslint-parser@8.0.1` e seu peer `@babel/core@8.0.1`, com parsing explícito de TypeScript e decorators legados. Babel só participa do lint: o build continua com `tsc`. A checagem de tipos, inclusive variáveis/parâmetros não usados, continua a cargo do TypeScript; não se declara lint com análise de tipos. Essa separação acompanha a [limitação documentada do parser Babel para regras TypeScript](https://babeljs.io/docs/babel-eslint-parser#typescript).

O lint resolve os caminhos relativos antes de avaliar as fronteiras e verifica imports, reexports, imports de tipos, `require` e imports dinâmicos:

- Domínio só depende de seu domínio e contratos compartilhados permitidos; não importa Node, Express, ORM, configuração ou aplicação.
- Aplicação depende do domínio, da própria aplicação/ports e de contratos explícitos de outros módulos; não importa adaptadores ou transporte.
- Tipos legados de persistência e `InfrastructureError` não atravessam essas fronteiras.
- Domínio/aplicação não acessam diretamente globais como `process`, `Buffer` ou `fetch`.
- Adaptadores não importam o HTTP de outro módulo.
- Os antigos aliases internos são rejeitados.

Há 15 fixtures de lint, incluindo casos permitidos e proibidos. Não foi necessário criar módulos vazios para exercitar essas regras: os testes usam caminhos virtuais da estrutura futura.

### Versão do Node e dependências

Node **22.23.2** foi fixado em `engines`, `.node-version` e Docker dev; o CI lê `.node-version`. A linha 22 consta como LTS no [calendário oficial](https://nodejs.org/en/about/previous-releases). O executável usado na validação foi conferido contra o [manifesto oficial de checksums da versão](https://nodejs.org/dist/v22.23.2/SHASUMS256.txt).

A instalação global encontrada era 22.19.0 e **não foi substituída**. A validação final usou um executável portátil 22.23.2 em `backend/tmp/e01-node`, junto da CLI npm 11.6.1 disponível na máquina. Para o desenvolvimento normal, selecione a versão de `.node-version` no seu gerenciador de Node. A pasta temporária está ignorada pelo Git e pelo contexto Docker.

`@types/node` passou de 26.5.0 para 22.20.2 para representar a linha de runtime escolhida; a dependência `undici-types` acompanhou essa mudança. Não houve atualização geral das dependências existentes. Zod, Supertest e parsers editoriais continuam para as etapas que efetivamente os utilizarão. Não foi executado `npm audit fix`.

### CI inicial e proteção dos ambientes

O workflow inicial executa os mesmos checks locais em Windows e Linux. Ele usa a configuração documentada por [checkout](https://github.com/actions/checkout) e [setup-node](https://github.com/actions/setup-node). A automação de release, banco, publicação editorial, imagem e restauração continua sendo ampliada nas etapas correspondentes, especialmente E12.

O exemplo de ambiente não foi copiado sobre nenhum arquivo pessoal. A consulta ao índice não encontrou arquivos de ambiente sensíveis rastreados; o histórico local consultado para `backend/.env.dev` não retornou commits. Isso não constitui auditoria de todos os remotos nem prova ausência de qualquer exposição histórica. A revisão pré-release definida no plano permanece para sua etapa, com rotação apenas se houver exposição confirmada.

## 5. Como executar a partir de agora

Execute os comandos dentro de `D:\Projetos\blog\backend`, com Node 22.23.2 selecionado:

```powershell
node --version
npm ci
npm run ci
```

Para verificações direcionadas:

```powershell
npm run lint
npm run typecheck
npm run test:unit
npm run test:integration
npm run build
```

`npm run ci` executa lint → typecheck → todas as suítes presentes/exigidas → build. Se uma etapa falhar, as próximas não mascaram seu resultado. A suíte de integração também recompila em isolamento para testar o artefato.

Para executar a aplicação local, crie `.env.dev` a partir de `.env.example` **somente se ainda não tiver seu arquivo local**, revise os valores e inicie o PostgreSQL:

```powershell
# Execute esta copia apenas se .env.dev ainda nao existir:
Copy-Item .env.example .env.dev
npm run dev:database
npm run build
npm start
```

O `npm start` não compila nem sobe o banco automaticamente. Ele executa o artefato já construído com a configuração existente. O carregamento atual usa `.env.dev` quando `NODE_ENV` não está definido; sua evolução e validação são trabalho da E02. `npm run dev` mantém o fluxo de desenvolvimento existente: sobe o banco local e inicia o watcher TypeScript.

## 6. Como interpretar os documentos nas próximas etapas

Os seis documentos principais não são seis backlogs separados. São perspectivas da **mesma etapa**:

1. **ORDER: qual trabalho vem agora?** Escolha a primeira etapa pendente e confira as dependências.
2. **PLAN: o que entregar?** Leia objetivo, estado atual, contratos, arquivos, implementação esperada e aceite da mesma E.
3. **BUSINESS_RULES: como deve se comportar?** Abra somente as regras R citadas e extraia validações, erros, restrições e exceções.
4. **STRUCTURE: onde implementar?** Confira a responsabilidade e o histórico do arquivo. Não crie toda a árvore antecipadamente.
5. **TEST_PLAN: como comprovar?** Implemente os cenários U/I/A exigidos junto do código; falha, concorrência e rollback também fazem parte da entrega quando previstos.
6. **ARCHITECTURE: por que essa decisão existe?** Consulte para entender responsabilidades ou resolver uma dúvida de desenho. Confronte descrições antigas do estado atual com o código e a auditoria mais recente.

Os códigos ajudam a fazer essa ligação: **P0** é a fase de primeira publicação; **E01** é uma etapa dessa fase; **R01** é uma regra; **E01-U01** e **E01-I01** identificam cenários unitário e de integração. Marcos como M0 agrupam entregas; não são implementações adicionais. Uma regra pode continuar sendo aplicada em várias etapas — por exemplo, a parte de imagem não root de R01 será concretizada em E11.

Há duas situações importantes para evitar interpretações erradas:

- **A árvore mostra o destino, e o histórico mostra quando chegar lá.** A STRUCTURE já apresenta `src/main.ts` e `src/infrastructures/logging/redact-sensitive.ts`. Em E01, seus componentes ainda ficam em `src/index.ts` e `src/infrastructures/logger/redact-sensitive.ts`. O histórico reserva os movimentos para E02. Criar os dois caminhos agora produziria duplicidade.
- **Comando futuro não é obrigação imediata.** A seção “Comandos operacionais esperados ao fim de P0” descreve o conjunto final da fase. Migrations entram em E03, validação editorial em E06 e import/publicação/seed em E07. Não crie scripts vazios para preencher essa lista antes de implementar suas responsabilidades.

Quando houver divergência, registre o que encontrou: arquitetura para intenção, auditoria/código atual para ponto de partida e contratos da etapa para execução. As anotações antigas “test quebrado” ou “aliases não resolvidos” permanecem como histórico do planejamento; a evidência de sua resolução está nos testes e neste registro. Não reexecute essas correções como se ainda estivessem pendentes.
