## 3. Contratos e decisões de execução

### Configuração explícita

`loadEnvironment` carrega `.env.dev` ou `.env.test` a partir da raiz do backend, independentemente do diretório de trabalho. A carga é silenciosa, não imprime valores, não modifica `process.env` e não sobrescreve variáveis já injetadas. Em `production`, nenhum arquivo de ambiente é carregado.

`loadConfig(env)` valida o objeto recebido e retorna configuração congelada, incluindo seus arrays e objeto de banco. Erros de configuração informam apenas nomes de campos; não retornam valores fornecidos.

| Variável | Contrato |
| --- | --- |
| `NODE_ENV` | `dev`, `test` ou `production`; ausência conserva o modo local `dev`. |
| `PORT` | Obrigatória; inteiro de 1 a 65535. A porta 0 só aparece nas fixtures que montam diretamente a configuração para um listener efêmero. |
| `DB_HOST`, `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD` | Obrigatórias. |
| `DB_PORT` | Inteiro de 1 a 65535; default 5432. |
| `DB_DIALECT` | Somente `postgres`; default postgres. |
| `DB_POOL_MAX` | Default 5. |
| `DB_ACQUIRE_MS` | Default 5000 ms. |
| `DB_STATEMENT_TIMEOUT_MS` | Default 3000 ms. |
| `PUBLIC_SITE_URL` | URL HTTP/HTTPS absoluta, sem credenciais/query/fragmento; HTTPS obrigatório em produção. |
| `CORS_ORIGINS` | Lista de origens HTTP/HTTPS sem path; espaços e duplicatas são normalizados; lista vazia permite apenas clientes sem Origin. |
| `TRUST_PROXY` | Vazio/false ou lista de IPs/CIDRs realmente controlados; `true`, nomes arbitrários, máscaras inválidas e redes `/0` são rejeitados. |
| `LOG_SERVICE` | Identificador simples de até 64 caracteres; default `blog-api`. |
| `SYNC` | Apenas ausente, vazio ou `false`. `true` é rejeitado. |

A remoção do caminho de `sequelize.sync()` foi feita já nesta adaptação do Database: a classe passou a receber apenas configuração validada, sem consultar ambiente para alterar schema. A E03 deverá preservar isso e acrescentar migrations, sem reintroduzir sincronização automática.

### Inicialização e encerramento

O fluxo é: validar ambiente → compor dependências → conectar ao banco → aguardar `listening` ou `error`. Falha de configuração encerra com código 1 sem imprimir valores; falha de conexão/listen fecha o pool e encerra com código 1. Um erro de bind não é tratado como servidor iniciado.

SIGTERM/SIGINT marcam `stopping` antes de drenar, fecham o listener, aguardam requisições em andamento e fecham o pool; o encerramento normal retorna 0. `uncaughtException`/`unhandledRejection` usam o mesmo fechamento com código 1. Rejeição do logger não bloqueia o fechamento. O deadline de 10 segundos permanece ativo durante a operação inteira; se for excedido, conexões HTTP são destruídas e o processo termina com 1.

Sinais durante a inicialização também marcam stopping. O fechamento aguarda a tentativa de startup antes de concluir, e a entrada verifica o estado antes de abrir o listener. Os handlers podem ser removidos em testes sem remover listeners de terceiros. Importar `main.ts` não inicia a aplicação: o bootstrap automático ocorre somente quando ele é a entrada executada.

### Health e limites de recursos

| Rota | Resposta |
| --- | --- |
| `GET /health/live` | `200 {"status":"UP"}`, independentemente do banco. |
| `GET /health/ready` | `200 {"status":"UP"}` quando disponível; `503 {"status":"DOWN"}` em falha, timeout ou shutdown. |

Ambas retornam `Cache-Control: no-store` e `X-Request-Id`. Não expõem ambiente, nomes internos, owners ou stack. `/api/` e `/api/health` foram substituídas e agora respondem 404.

Readiness espera até 1 segundo e compartilha uma única consulta pendente. Quando a resposta excede o prazo, novas verificações não enfileiram outras consultas enquanto aquela operação ainda não terminou. No PostgreSQL, a probe usa `SET LOCAL statement_timeout = 1000` dentro de uma transação curta, seguido de `SELECT 1`; o limite não contamina as próximas consultas da aplicação. Aquisição/conexão e execução também têm limites de driver. Esses mecanismos se baseiam nos [parâmetros do node-postgres](https://node-postgres.com/apis/client).

O HTTP segue a ordem: contexto → log de término → Helmet → CORS → limite de query/health/routers com parsers locais → 404 JSON → tratamento de erro. Não há parser urlencoded global, parser JSON global de 100 MB ou trust proxy irrestrito.

`jsonMutation` é um conjunto reutilizável de middlewares para futuras rotas de mutação: aceita `application/json`, limita o corpo a 16 KiB, rejeita JSON inválido com 400, excesso com 413 e tipo/codificação não suportados com 415. As rotas públicas de leitura não recebem esse parser. A query bruta tem limite de 2 KiB e excesso retorna `413 QUERY_TOO_LARGE`; validação de campos da query permanece para E09.

### Erros, correlação e logs

O envelope é:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Resource not found."
  },
  "requestId": "id-validado-ou-uuid-gerado"
}
```

`error.fields`, quando aplicável, contém somente `path`, `code` e mensagem segura, com quantidade e formato limitados. Detalhes extras e valores fornecidos não são repassados. As mensagens de `ApplicationError` e `HttpBoundaryError` devem ser constantes seguras escritas pelo adapter/caso de uso; não construa esses erros interpolando dados pessoais. Erros desconhecidos retornam `500 INTERNAL_ERROR`; indisponibilidade de conexão/pool conhecida retorna `503 DEPENDENCY_UNAVAILABLE`. Os kinds abrangem 400/401/403/404/409/422/429/503.

Se os headers já foram enviados, o handler chama `next` uma vez. O encerramento final da resposta parcial destrói o stream sem tentar outro JSON e sem deixar o handler padrão imprimir uma exceção privada. Erros de log, síncronos ou por Promise rejeitada, não impedem a resposta HTTP.

requestId/traceId aceitam somente `^[A-Za-z0-9._-]{1,128}$`; valores inválidos recebem UUID, inclusive no fallback do error handler. O AsyncLocalStorage mantém a correlação de requisições concorrentes.

Os logs conservam JSON/stdout e timestamp por evento. O evento de término contém método, template de rota ou `unmatched`, status, duração e código de erro quando houver. Não usa `originalUrl`, query, parâmetros concretos, cookies ou body. O formatter filtra os detalhes por allowlist; a redação anterior permanece como defesa adicional. Logs de erro HTTP/startup não serializam a exceção ou SQL arbitrários.

**Pipeline completo aprovado no Windows e no Linux, com Node 22.23.2: 28 testes por execução, zero falhas e zero testes ignorados.** Lint, typecheck e build também passaram. Os testes da E01 permaneceram no gate, inclusive instalação limpa pelo lockfile e execução do artefato após remover dependências de desenvolvimento.

| Cenário do plano | Evidência implementada |

| E02-U01 | Config inválida rejeitada sem secrets; defaults, normalização e imutabilidade; carga de arquivo local e bloqueio de arquivo em produção. |
| E02-U02 | Barreira entre requests concorrentes confirma IDs distintos; logs usam templates e não query/cookie/identidade concreta; IDs inválidos são rejeitados. |

| E02-I01 | Liveness independente do banco; readiness 503 por falha/prazo/shutdown; várias requisições não multiplicam a probe pendente; CORS e limites de parser no app isolado. |
| E02-I02 | Subprocesso com PostgreSQL real: request pendente conclui e ainda consulta o banco antes de fechar o pool; porta ocupada/conexão recusada retornam 1; fatal/rejeição encerram listener; SIGINT retorna 0; shutdown travado é forçado pelo timer. |
| E02-A01 | Respostas mínimas/no-store; CORS 403 com requestId, sem eco; JSON inválido 400; exatamente 16 KiB aceitos e 16 KiB + 1 rejeitado; tipo inválido 415; query excessiva 413; body não aparece nos logs. |
| E02-A02 | Envelope de erros de aplicação, erro interno sem stack/detalhes, dependência 503, IDs substituídos e término seguro de resposta parcial. |

No Windows, as fixtures emitem o evento de sinal no processo filho via IPC, pois o envio POSIX não está disponível da mesma forma. A suíte foi também executada em **Linux dentro de Docker**, onde os testes enviam **SIGTERM/SIGINT reais**. A distinção segue o [comportamento documentado do Node para sinais](https://nodejs.org/docs/latest-v22.x/api/process.html#signal-events).

O PostgreSQL de teste é `blog_test_e02`, isolado do banco de desenvolvimento, sem schema editorial ou dados pessoais. O cenário de timeout injeta um deadline reduzido somente na fixture; produção usa 10 segundos. O CI foi configurado, mas não foi disparado remotamente nesta sessão. O container executado aqui é infraestrutura de testes, não a imagem de produção da E11.

## 5. Como executar

Na pasta `D:\Projetos\blog\backend`, selecione Node 22.23.2 e instale pelo lockfile:

```powershell
npm ci
npm run test:database:up
npm run ci
npm run test:database:down
```

O banco de teste usa a porta local **15432** e armazenamento descartável. `test:database:down` remove apenas o ambiente `blog-e02-tests`; não usa o Compose de desenvolvimento. Os testes de integração falham se esse banco não estiver disponível, em vez de serem ignorados silenciosamente.

Sem banco, é possível executar os checks que não precisam dele:

```powershell
npm run lint
npm run typecheck
npm run test:unit
npm run test:api
npm run build
```

Para repetir o pipeline Linux completo com sinais reais:

```powershell
docker compose -f docker-compose-test.yml --profile checks run --rm checks
npm run test:database:down
```

O runner Linux monta as fontes para leitura e usa diretórios temporários próprios para dependências, artefatos e fixtures. Esses diretórios permitem a execução dos binários nativos de TypeScript/esbuild e desaparecem com o container. A instalação usa o lockfile e não altera o `node_modules` do host.

Para desenvolver/executar a API, revise seu `.env.dev` usando o exemplo atualizado. **Acrescente `PUBLIC_SITE_URL` se seu ambiente antigo ainda não a tiver**; `PORT` e os dados de banco também são obrigatórios. Não sobrescreva suas credenciais locais com a cópia do exemplo.

```powershell
npm run dev
# Alternativa com artefato compilado, depois de disponibilizar o banco:
npm run build
npm start
```

A entrada compilada agora é `dist/src/main.js`. Consulte `/health/live` e `/health/ready`. Em produção, injete as variáveis explicitamente, use URL pública HTTPS e declare somente as redes de proxy sob seu controle.
